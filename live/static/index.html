§1 problem

What telos is

The problem

Modern satellite and constellation operations are telemetry-heavy but human-triage-heavy. Anomaly detection is largely solved — LSTM-based streaming detectors work well in production at NASA, ESA, and most commercial operators. What is not solved is everything after detection: diagnosing the cause across interdependent subsystems, proposing a recovery procedure that is known-safe and known-effective, validating it before committing, approving it under the right human-in-the-loop gate, executing it with per-step receipts, and verifying the outcome with a tamper-evident runbook that survives the 7-year retention window regulators and insurers require.

Each of these is a separate tool, a separate team, a separate context switch in the operator's day. As constellations scale from 1 to 10 to 100 to 1000 satellites, the human-triage model breaks.

The intended outcome

telos is a reference architecture for ops centers that want to automate the post-detection pipeline. It is a runnable prototype demonstrating Detect → Diagnose → Propose → Validate against synthetic satellite telemetry, and a vehicle for exploring how the trust, approval, and audit pieces fit together before they get wired into a real ops center.

Scope — what it is, and is not

It is not a production-ready ops system. No real flight hardware. No real regulatory certification. It is not an LLM-agents framework — the LLM is a future narrator, not a peer agent. It is not a physics-accurate simulator; the twin is a deterministic state machine, enough to demonstrate the validation contract, not enough to replace mission sims. It is not a general anomaly-detection library; detection is reused from the existing live/ pipeline. telos focuses on the stages after detection.

§2 pipeline

The 7-stage pipeline

Fig. 1 — Stage 1–4 are shipping (solid teal). Stages 5–7 are deferred to Phase 2/3 (dashed grey). The Phase 1 boundary is structural: there is no code path that crosses it in Phase 1.

Stage 1 — Detect

Continuously scores live telemetry against an LSTM-predicted baseline, smooths the prediction error with an EWMA filter, runs the telemanom thresholding pipeline on the smoothed-error window, and emits a per-channel deviation signal. Lives in live/: FastAPI server, LSTM runner, streaming error pipeline, synthetic generator, config. Five modules, ~1,000 lines.

Stage 2 — Diagnose

Given a window of SymptomEvents, scores every cause in the registry against the window's evidence and returns the ranked list. The score is a sum of three terms (+1.0 per channel-overlap event, +0.5 per subsystem-overlap event, +0.25 stickiness bonus per additional matching event); the threshold is MIN_DIAGNOSE_SCORE = 0.5. The rubric is independent of how the symptom events were generated — Diagnose does not know if they came from a live LSTM alert or a synthetic seeding. twin/diagnose.py, 152 lines.

Stage 3 — Propose

Given a cause and the current twin state, picks the best procedure by twin-validated risk — not by catalog rank or default_procedure_id. Two-stage selection: pre-filter candidates to PROPOSE_TOP_K = 5 by catalog-level effort_score / mission_impact / reversibility (D-16), then validate all top-K in parallel in a ThreadPoolExecutor (D-17). The twin is the source of truth for "what will happen if I apply procedure X to state S" — letting it do the ranking means Propose is honest. Multi-axis lexicographic ranking (D-19) is the final arbiter: (mission_impact_score, effort_score, reversibility_score, risk_score), ascending. The RankedCandidate dataclass (D-18) carries the catalog fields through so the runbook renders the same logic the operator sees.

Stage 4 — Validate

Projects the twin forward from a starting state with a proposed procedure applied — twice. Once with the procedure, once without. The two-trajectory model gives the operator the delta: predicted vs baseline arrays keyed by state field, 31 points each over the default 1-hour horizon. Six constraints are checked per timestep (battery_soc, battery_voltage_v, battery_temp_c, electronics_temp_c, payload_temp_c, pointing_error_deg). The verdict wrapper maps the result to OK | REJECT | INCONCLUSIVE with RISK_THRESHOLD_INCONCLUSIVE = 0.3.

Stages 5–7 — deferred

Stage 5 (Approve) is Phase 2: the policy-gated operator approval with the 4-class risk scheme and the LLM locked out of the gate by structure, not by prompt. Stage 6 (Execute) is Phase 2: a CommandBus walking the approved procedure with per-step input/output hashes and operator signatures. Stage 7 (Verify) is Phase 3: a Merkle-chained runbook, content-addressed evidence (evidence://<sha256>), and a replay harness that survives the 7-year retention window.

Why the catalog is one file (D-10)

The cause enum, the procedure enum, the parameter schemas (with bounds), the precondition/postcondition predicates, the approval requirement per procedure, and the twin's apply_procedure() function are all defined in a single Python module. The catalog cannot lie about what the twin can do, because both come from the same file. The cost is that editing the catalog is editing code (it goes through the same review as code); the benefit is that drift is structurally impossible.

§4 bridge

The bridge — the single seam

live/twin_bridge.py (~470 lines) is the only module in live/ that imports from twin/. It exposes two public functions (inject_fault and run_phase1_pipeline) and two public tables (INJECTION_TO_FAULT with 13 entries, CHANNEL_TO_SUBSYSTEM with 8 entries).

The lazy-import pattern (_ensure_twin_on_path() at the top of every twin-using function) keeps live/ws_server.py bootable on system Python without the CHESS astropy chain. If the CHESS venv is missing, run_phase1_pipeline() returns None; the live server keeps running; /inject_twin_fault returns 503. This is the right behavior: tell the operator the feature is unavailable, don't crash.

"Putting all the cross-boundary knowledge in one file makes it auditable, testable in isolation, and replaceable — to a gRPC twin in Phase 2 — without touching the rest of live/." — D-14, the bridge is the only place live/ imports from twin/
§5 trust

Trust, approval, and the LLM boundary

The system has a structural answer to the question "where does the human stand in front of the machine?" The answer is: the human is the only thing the machine cannot bypass. The LLM has no path to the approval gate. This is enforced structurally — the LLM's tool surface does not include the gate — not by prompt. The four-class risk scheme (A/B/C/D) is the policy layer; the 30-second hold-down timer and the 2-person rule for Class D are the procedural layer; the dry-run preview UI is the operator's view.

What the LLM is and is not

In Phase 1, the LLM is nothing. There is no narrator protocol, no LLM SDK in requirements, no API keys in the repo. The structured outputs (Diagnosis, Proposal, Verdict) carry only structured data; prose is added in Phase 4 as a post-processor.

In Phase 4, the LLM will write prose around the already-structured outputs. The narrator cannot change the cause Diagnose picked, cannot change the procedure Propose picked, cannot issue an ApprovalToken. Every claim in the narrative must map to a catalog entry or an evidence ref. The narrator is a pure function of its inputs in tests.

§6 runbook

The runbook

The runbook is the operator-facing artifact the dashboard renders after an injection. It is built once at inject time (per the BIBLE §2 predictive-pipeline contract) and persists across page refreshes via the in-memory RunbookStore (a thread-safe FIFO capped at 50 entries, ids of the form RB-YYYYMMDD-NNNN).
